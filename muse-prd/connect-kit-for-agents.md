# AIメシモリ 接続キット（他の Muse エージェント向け）

これは、AIメシモリ（食事・体重の記録サービス）を「あなたのユーザー」の記録先として使うための手順書です。
AIseki には人間の入力UIがありません。記録はエージェント（あなた）が API へ送り、ユーザーは PWA で眺めるだけです。

> ステータス: ローカル版（prd ブランチ＝配布版。main は開発用で、プルリクの提出先）。各 Muse が自分の環境で動かす版で、認証・鍵・公開URLは使わない。
> オンライン版（AIthlon 認証）は online-aithlon ブランチに分離してある。

## 1. 接続（ローカル版）

自分の環境で動いている AIメシモリ API（既定: http://localhost:8787）の `/graphql` に直接リクエストを送る。認証は不要（localhost 内の単一テナント運用）。起動方法は `prd/local-setup-for-agents.md` を参照。

## 2. 記録の送り方（GraphQL）

エンドポイント: `POST {{BASE_URL}}/graphql`（署名付き）

- 食事: `upsertMeal(input)` — 作成も訂正も同じ mutation。主キーは `external_id = meal-YYYYMMDD-{区分スラッグ}-{連番}`。
  - 区分スラッグ: asa=朝食、hiru=昼食、yuu=夕食、oyatsu=おやつ、yashoku=夜食、other=その他。連番は (date, 区分) に対して tz をまたいで通し番号。
  - kcal は中央値＋±（kcal / kcal_pm）。確定値は pm=0。栄養素も同形式、不明は null。
  - status: planned／actual／skipped（skipped は「食べなかった」宣言、menu/items 不要、kcal=0）。合計に数えるのは actual のみ。
  - 時刻は現地の経過表記（深夜は 24:41 のように書く。所属日 date は別フィールドで、時刻から導出しない）。
  - tz を省略するとテナントの「現在の滞在tz」で解決され、保存時に焼き込まれる。既存レコードと tz が食い違う external_id の再送はエラーになる。
  - items（内訳）がある場合、value_source は自動判定される（全部公式→公式値、混在→混在、全部推定→推定）。
  - place は自由文字列（例: 「セブンイレブン（購入）」のように購入は接尾辞で表す）。
  - emoji: その食事の絵文字を1つ付けるのが原則。メニュー名から自動選択し、文脈で調整してよい（検証: 書記素クラスタ1つまで。ZWJ連結は1つとして数える）。
- 日次: `upsertDay(input)` — `external_id = daily-YYYYMMDD-{都市スラッグ}`。体重・体脂肪・BMI（欠損可）、体調メモ。
  - emoji: その日のスタンプを1つ。代表メニューに限らず、場所・出来事・気分でもよい（例: 🐷、☕）。その日の締めに選ぶ。

## 3. 毎日の運用

1. ユーザーとの会話・レシート・写真などから食事を組み立て、その都度 upsertMeal で送る（訂正は同じ external_id の再送）。
2. 体重を聞いたら upsertDay で送る。1日の締めに days.emoji を選ぶ。
3. 取得して確認したいときは `calendar(month)` / `day(date)` / `weightSeries(from,to)` / `me` を必要なカラムだけ指定して引く。

## 4. 記録の会話フロー（写真が来たら）

1. 利用者から食事の写真や情報が届いたら、内容を読み取る（メニュー・量・店など）。
2. 足りない情報だけを簡単な質問で確認する（例: 食べた時刻、区分の確認、量の調整）。聞くのは最小限。
3. データを構造化し（§2 のルール: 中央値+±、区分、スタンプ絵文字）、upsertMeal で投入する。
4. 投入したら「📊 画面を見せて」ボタンを提示し直す（§5 の画面をいつでも開けるように）。
5. 体重は upsertDay で記録する。

**人間への見せ方（推奨）**: 記録した内容や1日のまとめを人間に見せるときは、表形式がおすすめ（時刻・メニュー・kcal・スタンプ絵文字を並べると一目で分かる）。人間向けの文面は絵文字を使って楽しく——絵文字スタンプはこのアプリの可愛さであり、日記みたいに読み返せる楽しさの本体。ヘルスケア系のデータソース（健康アプリのエクスポートや連携コネクタ等）から体重が取れる環境では、利用者の了承のもと、そこから取り込んで記録してもよい。

## 5. 画面の見せ方（「画面見せて」と言われたら）

ライブブラウザで PWA を操作して見せる方式は禁止（重い・遅い・壊れやすい、という運用判断で確定）。確定方式は「元ファイル＋データ流し込み」:

1. 土台はリポジトリ内のモック最新版の単一HTML（shared/mockup/aiseki-mockup.html）。
2. GraphQL（calendar / day / weightSeries / me）で最新データを取得し、モック内のデータブロック（DAYS / TARGET / TOT / SHORT / WEIGHTS / MEAL_EMOJI / DAY_EMOJI / selectedDate）だけを実データで置換したHTMLを生成する。HTML本体をエージェントが書き起こさない（トークン消費最小・表示はモックの進化に自動で追随）。
3. 生成したHTMLファイルをチャットで提示する（ファイル名や置き場は各家庭の運用で決めてよい）。
4. データブロックの変数名・形式は流し込みの契約面。モック側で構造を変えた場合は、生成側へ一報して追随してもらう。
7. 肥大化防止（生成ファイルは2版制）:
   - **focus版（日常用）**: 対象月の前3ヶ月＋翌1ヶ月を、詳細（DAYS / MEAL_EMOJI）含め全ブロック流し込む。翌月分は予定（planned）を見るために含める。実測 約87KB（5ヶ月・145日）。
   - **long版（全期間）**: 全期間を流し込む。実測 約217KB（14ヶ月・417日）。歯止めはファイルサイズ: 1MB に近づいたら古い月から詳細（DAYS / MEAL_EMOJI）を段階的に落とす（色・スタンプは TOT / DAY_EMOJI で残る）。
   - 生成時にバッジ（#editionBadge）のテキストを版名（focus / long）に差し替える。
   - テンプレートの月移動は、流し込んだデータの範囲内に自動で制限される（範囲外の月には進めない）。
6. ユーザーが自分で PWA を開いて眺めるのは「見る」の範囲であり、役割分担と矛盾しない（あくまで補助経路。主経路はこの流し込み表示）。
8. アーティファクト版の家庭では、2 のデータ取得元は GraphQL ではなくアーティファクトのアクション（get_month / get_day）を使う。取得した JSON を流し込み生成へ渡し、以降の手順は同じ（2026-11-01 追記）。
## 6. やってはいけないこと

- 秘密鍵・署名材料をチャット本文や外部サービスに出さない。
- ユーザーの承認（claim）なしに接続を進めない。
- 他テナントのデータを推測・要求しない（あなたの署名鍵のテナント分しか見えない）。
