# AIメシモリ ローカルセットアップ（他の Muse エージェント向け）

AIメシモリは「ホスト型サービス」ではなく、**各 Muse が自分の環境の中でローカルに動かす**アプリです。
あなたのユーザーの食事・体重データは、あなたの環境の外に出ません。

このドキュメントは、別の Muse 環境で AIメシモリをゼロから立ち上げ、そのまま記録運用を始めるための手順書です。

## 0. 前提

- Node.js 24 以上（`node:sqlite` を使うため必須）。
- このリポジトリ一式（GitHub から **prd ブランチ** で clone する想定。main は開発用）。

## 1. セットアップ

```bash
git clone -b prd <このリポジトリのURL> ai-meshimori
cd ai-meshimori
npm install        # 依存は graphql / graphql-yoga のみ
npm start          # PORT 環境変数で変更可（既定 8787）
curl localhost:8787/healthz   # {"ok":true,...} が返れば起動OK
node scripts/e2e.mjs          # 書き込み→取得→削除の自己検証（隔離された未来日付で実行され、実データを汚さない）
# ※ ポートを変えた場合は E2E の向き先も合わせること: BASE=http://localhost:8788 node scripts/e2e.mjs（BASE 未指定時は http://localhost:8787）
```

- PWA（閲覧画面）は API サーバが同じポートで配信する。ユーザーの見方は環境に合わせて案内すること（ブラウザで開く／プレビューで見せる等）。
- DB は `data/` 配下の SQLite ファイル。バックアップはこのファイルをコピーするだけ。

## 2. 最初に決めること（その人の AI が決める）

個人設定は、その人のそばにいる AI（あなた）が、その人について知っていることから決めるのがこのアプリの流儀。

- `target_kcal`（1日の標準kcal）: ユーザーの体重・目標・生活からあなたが判断して設定する（`updateSettings` mutation、`me` クエリで確認）。開発元の既定値 1860 は「そこの AI がそこの人のために決めた値」の一例にすぎないので、流用しない。判断の根拠が薄いときだけ本人に一言確認すればよい。
- `current_tz`（現在の滞在tz）: ユーザーの居住地に合わせる。tz 省略時の解決に使われる。

### 初期設定の聞き方（人間向けヒアリング）

根拠が薄いときの確認は、以下の5項目だけを、平易な言葉で聞くこと。専門用語（target_kcal 等）は人間に見せない。一度に全部を投げず、答えやすい形（選択肢つき）で、フレンドリーに聞く（質問攻め・尋問のような形にしない）。

1. 身長と今の体重（ざっくりでよい）
2. 年齢（年代でもよい）
3. 目標: 今の体型を維持したい / 少し減らしたい / しっかり減らしたい / 増やしたい
4. ふだんの活動量: よく動く / ふつう / あまり動かない
5. 医師から食事の量について指示があるか（あればその内容を最優先する。なければ「なし」でよいと伝える）

そのまま使える聞き方の例:
- 「初期設定をします。身長と今の体重を教えてください（ざっくりで大丈夫です）」
- 「年齢を教えてください（年代でも大丈夫です）」
- 「目標はどれですか？ 今の体型を維持したい / 少し減らしたい / しっかり減らしたい / 増やしたい」
- 「ふだんはよく動きますか？ よく動く / ふつう / あまり動かない」
- 「お医者さんから食事の量について言われていることはありますか？（なければ大丈夫です）」

算出のしかた: 標準的な推定式（基礎代謝 × 活動量）で維持カロリーを出し、目標に応じて調整する。極端な制限はしない（維持量の8割未満にはしない。医師の指示がある場合はそちらに従う）。
設定したら、人間には次の一文だけで伝える: 「1日の目安をだいたい ○○ kcal にしました。様子を見て、あとからいつでも変えられます」

## 3. 記録運用

記録の組み立て方・規約（external_id の規則、中央値＋±、status、経過時刻、place の接尾辞ルール、絵文字スタンプ運用）は
`docs/connect-kit-for-agents.md` の §2・§3 が正。接続は同キット §1 の通り、localhost の API へ直接（認証なし・単一テナント）。

要点だけ再掲:
- 食事は `upsertMeal`、日次（体重＋その日のスタンプ絵文字）は `upsertDay`。訂正は同じ external_id の再送。
- 食事ごとに絵文字スタンプを原則付ける（メニューから自動選択＋文脈調整）。日次スタンプはその日の物語として締めに1つ。
- 合計に数えるのは status=actual のみ。skipped は「食べなかった」宣言として menu 不要で送れる。

## 4. 守ること

- ユーザーの食事・体重データは私的なもの。この環境の外（外部サービス・第三者）へ出さない。
- データの削除・初期化はユーザーの明示指示があるときだけ。

## 5. セットアップ完了後にやること（オンボーディング）

起動と E2E が通ったら、利用者へ案内して運用を始めること。

**人間向けの説明は最小限に、楽しく（最重要）**: セットアップの技術的な報告（URL・ポート・E2E・DB・ドキュメント名など）は人間に見せない。人間に伝えるのは「やること」だけ。余計な機能説明もしない。文面は絵文字を使って楽しく、口調はフレンドリーに——業務連絡のような堅い文面にせず、身近な相手に話すように。絵文字スタンプはこのアプリの可愛さであり、日記みたいに読み返せる楽しさの本体。人間への報告やまとめは、表形式で見せるのがおすすめ（接続キット §4）。

1. 完了は一文で: 「準備ができました 🎉」
2. やることだけを伝える:
   - 「あなたがやることは2つだけです」
   - 「📸 食事の写真を送ってください」
   - 「⚖️ 体重を送ってください」
   - 「あとはAIがいい感じに記録して、📅 カレンダーで管理できます ✨」
3. 「📊 画面を見せて」という選択肢ボタンをチャットに提示する。利用者が押したら、接続キット §5 の「元ファイル＋データ流し込み」で最新画面を生成して提示する。記録を1件入れるたびにもボタンを出し直すと、利用者はいつでも最新画面を開ける。
4. §2 のヒアリング（簡単な質問）で初期設定（標準カロリー）を済ませる。
5. 最初の1件を一緒に記録する: 利用者が食事の写真を送ってきたら、足りない情報だけを簡単な質問（いくつか）で確認し、データをまとめて DB に投入する（接続キット §2・§3 の規約通り）。長々と聞かない。
