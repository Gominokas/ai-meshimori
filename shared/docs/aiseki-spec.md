# AIメシモリ 仕様書（実装引き継ぎ版、開発コードネーム: AIseki）

食事記録サービス **AIメシモリ** の確定仕様。2026-10-31 にアプリアイデア窓で設計を固めた内容を、実装用に整理したもの。
経緯と決定の履歴は設計メモ（~/workspace/app-ideas/meal-viewer-design.md、決定事項1〜37）を参照。認証方式の単体まとめは ~/workspace/app-ideas/ai-agent-auth-protocol.md。

- 運用開始目標: 2026年11月（まず個人利用で回し、最終形はマルチユーザのサービス）
- 入力経路: AI（当面はダイエット窓のセリナ）がAPIへ直接送る。表示にAIは関与しない
- 設計原則: ストーリーが最初。1日の物語（現地で経験した日付と時刻）が正本で、仕様はその抜け漏れを炙り出すために書く

## 1. プロダクト概要

- AIが食事と体重の記録をAPIで送り、人間はフロント（PWA）で眺めるサービス。
- 送信側の契約は「決められたJSON形式で送る」ことだけ。コメント・備考が欲しいときだけ GraphQL でそのカラムを取る。
- AIが疲れないことが設計要件: 仲介チャットなし、書き込みは upsert 1発、時刻換算は取り込み時に一度だけ確定、取得は必要カラムだけ小さく返す。

## 2. ビューア要件

- 月カレンダー: 各日のマスに体重と合計kcal。月をめくって過去も見られる。
- 日詳細: その日の食事一覧（食事区分・メニュー・kcal・備考）。並びは eaten_time 昇順、時刻なしは区分順（朝食→昼食→おやつ→夕食→夜食→その他）。
- 週の開始は月曜デフォルト（設定で変更可）。
- カレンダー本物の予定には入れない。自動浮上（去年の同日等）はしない。
- kcal表示: 中央値±pm からレンジ復元（745±45 → 700〜790）。pm=0 は単一値。日次合計は actual の中央値合計が主表示、日詳細では合計レンジも出す。
- status の色（仮デフォルト、試して直す）: actual＝緑系、planned＝青系、skipped＝グレー。
- 時刻の使い分け: 食事メニューは現地日時、グラフ系（体重推移など時系列）は標準日時。両方とも保存済みカラムで、再計算なし。
- 同じ日付に複数 tz の日がある場合: カレンダーのマスは日付単位で全 tz 合算（体重は tz 短縮ラベル付きで縦併記、例「東京 101.8／LA 100.2」）、日詳細は (date, tz) ごとに節を分ける。

## 3. データモデル

キモの規則:

- **date（所属日）は権威ある独立フィールド**。タイムスタンプから日付を導出しない。日付を動かす仕組み（day_offset等）はない。
- 時刻は二重持ち: 現地（date＋eaten_time）と標準＝日本標準時（std_date＋std_time）を対で保存する。標準側は取り込み時に送信側が確定させ、サーバは後から換算し直さない。国内では現地＝標準の同一値を対にする。
- 日のキーは (date, tz)。日付変更線ケース（東京の26日朝食と、線を跨いだ先のアメリカの26日朝食）が両方正しく存在できる。
- tz が省略されたら、アプリの「現在の滞在tz」設定で解決し、保存時は解決済みの値を焼き込む（後から設定を変えても過去は書き換わらない）。

### meals（1食＝1レコード。定食・弁当のような複数品のまとまりも1件）

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| external_id | string | 必須 | 主キー扱い。`meal-YYYYMMDD-{区分スラッグ}-{連番}`。同キー再送＝上書き（upsert） |
| date | date | 必須 | 所属日（現地） |
| tz | string | 任意 | IANA tz。出所メモ（日のキー識別に使う） |
| utc_offset | string | 任意 | その日時点のオフセットのスナップショット（例 +09:00） |
| eaten_time | string / null | 任意 | 現地の経過時刻 `^\d{2}:[0-5]\d$`、00:00〜99:59。深夜の夜食は前日所属で 24:41 と書ける。表示・並び専用で日付は動かさない |
| std_date / std_time | date / string | 任意 | 標準日時（日本標準時）。std_time は通常時計表記 00:00〜23:59（経過表記は現地側だけ） |
| meal_type | enum | 必須 | 朝食／昼食／夕食／おやつ／夜食／その他 |
| tags | string[] | 任意 | 自由タグ（例: 追い、ブースト） |
| status | enum | 必須 | planned／actual／skipped。skipped は「食べなかった」宣言で kcal=0、未記録と区別する。合計に数えるのは actual のみ |
| menu | string | 条件付き | まとまりの名前。items のみでも受理するがどちらか必須 |
| kcal / kcal_pm | integer | 必須 | 中央値＋±値。集計は中央値だけ。確定値は pm=0 |
| protein_g / protein_pm、fat_g / fat_pm、carbs_g / carbs_pm、salt_g / salt_pm | number / null | 任意 | 栄養素も中央値＋±で統一。不明は null |
| value_source | enum | 任意 | 公式値／推定。items がある場合は自動判定が優先 |
| report_source | enum | 必須 | レシート／写真／申告／レシピ |
| items | array | 任意 | 内訳（下記）。無くても受理 |
| note | string | 任意 | 備考 |
| place | string | 任意 | 食べた／買った場所（自由文字列。例: セブンイレブン（購入）） |
| emoji | string | 任意 | その食事の絵文字1つ。送信側AIが原則付ける（メニュー名からの自動選択＋文脈で調整。人間の手間はゼロという前提で、2026-10-31にダーリン判断・ダイエット窓合意）。日詳細のカードや凡例に表示。カレンダーのセルは days.emoji を優先し、無い場合は代表メニュー（最大kcalの actual）の emoji→メニュー名推定→🍽️ の順でフォールバック |
items: name（必須）、kcal／kcal_pm（任意）、value_source（公式値／推定、品目ごと）、栄養素は任意で同形式。
レコード全体の value_source 表示は items から自動判定: 全部公式→公式値、混在→混在、全部推定→推定。

区分スラッグ: `asa`=朝食、`hiru`=昼食、`yuu`=夕食、`oyatsu`=おやつ、`yashoku`=夜食、`other`=その他。
語彙の対応付け: 追い朝食→ asa＋タグ「追い」、間食→ oyatsu、ブースト→区分にせずタグ／備考へ。
食事の連番は (date, 区分) に対して **tz をまたいで通し番号**。upsert 時に既存レコードと tz が食い違う external_id が来たら、黙って上書きせずエラーで返す。

### days（日次。(date, tz) が自然キー、upsert）

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| external_id | string | 必須 | `daily-YYYYMMDD-{都市スラッグ}`（例 daily-20261026-tokyo、daily-20261026-losangeles） |
| date / tz | date / string | 必須 | 複合キー。tz は送信時任意・保存時必須 |
| measured_time | string / null | 任意 | 計測のおおよその時間（現地） |
| std_date / std_time | date / string | 任意 | 計測の標準日時版。体重グラフはこちらで引く |
| weight_kg / body_fat_pct / bmi | number | 任意 | 欠損可（体重がない日がある） |
| steps / exercise_minutes / exercise_kcal | number | 任意 | 運動データ（歩数・運動時間（分）・活動消費kcal）。送信側AIがヘルスケアデータ（Apple Health 等）から日次に自動取り込みする想定で、手入力は前提にしない（2026-11-01 追加） |
| condition_note | string | 任意 | 体調メモ |
| emoji | string | 任意 | その日のスタンプ絵文字1つ。代表メニュー・場所・出来事など、その日を象徴するもの（例: 🐷とんかつ三昧、☕カフェ作業）。送信側AIが日次記録と一緒に付ける。カレンダーのセル表示に使い、未指定時は代表メニューからの推定→🍽️ の順でフォールバック |

合計kcalは保存しない。meals の actual 中央値を都度集計する。

## 4. API

- 取得・書き込みとも **GraphQL** に統一する。取得はカラム指定型（呼ぶ側が欲しいフィールドと形を決め、その通りのJSONが返る）。書き込み（upsert／削除）は mutation。
- 書き込みの意味論は external_id upsert: 作成も訂正も同じ mutation で、同じ external_id の再送が上書きになる（GET→PUT の2段階にしない）。
- 送信JSONの実例（1行＝1レコードのJSONLと同形）:

```json
{"external_id":"meal-20261029-yashoku-01","date":"2026-10-29","eaten_time":"24:41","meal_type":"夜食","tags":["ブースト"],"status":"actual","menu":"セブンイレブン夜食セット","kcal":850,"kcal_pm":80,"report_source":"レシート","note":"実時刻は翌日0:41だが所属日は10/29"}
{"external_id":"daily-20261028-tokyo","tz":"Asia/Tokyo","date":"2026-10-28","weight_kg":101.8,"body_fat_pct":33.8,"bmi":30.1,"condition_note":""}
```

## 5. 認証: AIthlon方式

生のAPIキーは発行しない。詳細は単体ドキュメント（ai-agent-auth-protocol.md）が正。

### フロー（開始はAIから）

| # | 手順 |
|---|---|
| 1 | AIが discovery を取得: `GET /.well-known/aithlon.json`（固定URL、JSON 1発。版数・エンドポイント・公開パラメータを返す。OIDC discovery と同じ流儀） |
| 2 | AIが鍵ペア（Ed25519想定）を生成し、公開鍵でサインアップ。サーバは pending 登録と claim URL を返す。秘密鍵はAIから出ない |
| 3 | AIが claim URL を人間に渡す |
| 4 | 人間が claim URL を開き Google でサインイン（OIDC。サービスはパスワードを持たない） |
| 5 | サインイン後の画面が連携ブロブを表示し「5分以内にAIへ連携」を促す。ブロブは同内容JSONを、コピペ用 base64url 1行文字列と `.json` ファイルの併用形で渡す |
| 6 | 並行チャレンジ（下記）を通過し、AIがブロブ＋秘密鍵の署名で最終登録 → active。以後のAPI呼び出しはリクエスト署名で認証 |

### 並行チャレンジ（GET 2本レース）

- GETを2本同時に走らせる。どちらが速いかはセッションごとにサーバがランダム（初期値: 速い方0.3秒／遅い方5秒）。
- クライアントは先に返ってきた方の問題を解き、遅い方が完了する前にPOSTで返す（POSTにも署名）。
- サーバ検証: 2本の開始がほぼ同時／POSTが遅い方の完了より前／答えた問題IDが速かった方と一致／署名が正しい。
- 狙いは「AIネイティブでないと、まず返答ができない」構造。人間の逐次操作と、道具を持たない会話だけのLLMは通らない。

### 紐付けと失効

- 正本はサーバ側レコード: Google sub ⇔ テナント ⇔ 公開鍵。claim URL は識別子であり秘密ではない（漏れてもGoogle認証で止まる）。
- 鍵の状態: pending → active → revoked / expired。失効は不可逆。
- 失効経路: ①管理画面（Googleログイン）から即時失効 ②全鍵パニック失効 ③AIの自己ローテーション（旧鍵の署名で新鍵へ交代、系譜を記録） ④TTL自然失効。
- パラメータ初期値: 鍵TTL 90日／ローテーション併用猶予 24時間／連携ブロブ期限 5分（いずれも実測で調整）。
- 鍵の登録・失効・交代は監査ログに残し、人間に通知する。
- 残件: 秘密鍵保管はプラットフォーム依存のため「安全な保管と署名ができること」を適合要件として規定するに留める。鍵のラベル／スコープのデフォルトは実装時に決める。

## 6. 実装形態

- バックエンド: 独立した小さなAPI（GraphQL）＋フロントはPWA（ホーム画面に置ける、iOS／Android両対応）。
- ホスティング: コンテナ基盤（自宅シェアハウスのため自宅サーバ不可）。Fly.io か Cloud Run かは着手時に最終選定（強み比較は設計メモ決定事項33）。
- デプロイ制約: レースのため、接続保持と応答タイミング制御・同時接続・セッション状態共有が要る。純サーバレス関数は原則不適合。コンテナなら移行は再デプロイで済むので基盤選定は可逆。
- 段取り: フェーズ1＝個人利用で11月運用開始 → フェーズ2＝使い勝手とデータ量を検証 → フェーズ3＝マルチユーザ化（サービス）。任意で Capacitor 等のネイティブ化（APIはそのまま）。
