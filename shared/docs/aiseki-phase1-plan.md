## 0. フェーズ1のゴール定義（最小構成で「回る」状態）

1. セリナ（AI）がスクリプトから直接APIへ meals / days を upsert できる
2. ダーリンがスマホのPWAで月カレンダー＋日詳細＋体重推移を見られる
3. 接続は生APIキーではなく AIthlon（公開鍵＋Google claim＋GET 2本レース＋署名）で成立する
4. 2026年10月分（log-2026-10.md）が初期データとして画面に出る
5. 全部コンテナ1台で動き、Fly.io ⇄ Cloud Run の移行が Dockerfile 差し替えで済む

ここまでがフェーズ1。マルチユーザ一般公開・ネイティブ化・通知は入れない。

## 1. 推奨スタック（案）

| 領域 | 推奨 | 理由 |
|---|---|---|
| 言語 | TypeScript / Node 22 | API・PWA・AI側クライアントを同言語で揃える。Ed25519は Node 標準 crypto で署名/検証可。型を GraphQL スキーマと共有しやすい |
| API枠 | Fastify + GraphQL Yoga | 軽量・常駐向き。Yogaはファイルに縛られず、レース用RESTエンドポイント（discovery / signup / race / claim）を同じプロセスに同居できる |
| DB | PostgreSQL + Drizzle ORM | (date, tz) 複合キー、JSONB（items / tags）、将来のマルチテナントに耐える。開発時は Docker の pg、 本番は Fly Postgres / Neon のどちらでも接続文字列差し替えのみ |
| 認証（人間） | Google OIDC（openid-client） | サービスはパスワードを持たない。sub を正本にする（仕様 §5） |
| 認証（AI） | Ed25519 リクエスト署名 | 正本ドキュメント通り。canonical = method + path + timestamp + body-hash、±5分窓＋nonceでリプレイ防止 |
| PWA | Vite + React + vite-plugin-pwa + Tailwind | カレンダーは自前グリッドで十分。ホーム画面追加・オフライン殻だけ先に、データは常にAPI |
| 構成 | pnpm monorepo: apps/api, apps/web, packages/shared（型・スラッグ辞書・バリデーション） | external_id 規則や eaten_time 正規表現 `^\d{2}:[0-5]\d$` を API / クライアントで二重実装しない |
| 配置 | Dockerfile 1本（api が web の静的成果物も配信） | フェーズ1は配信面を1つに寄せる。分離はサービス化時 |

代替を捨てる理由メモ: SvelteKit単体で全部やる案はレースのタイミング制御と GraphQL 同居がやや窮屈。Go案は型共有が切れる。Python案はPWA側と二言語になる。いずれも不可ではないが、個人開発の速度では TS 統一が勝つ。

## 2. ホスティング選定案（未確定点1への回答案）

**フェーズ1は Fly.io を推す。**

- レース（速い0.3秒／遅い5秒）はコールドスタート無しの常駐1台が一番素直。状態をプロセス内＋DBで完結できる
- 小額固定で請求が読める。個人利用のトラフィックなら最小マシンで足りる
- Cloud Run は Google 生態系（OIDC / ログ / IAM）と無料枠・スケールが強いが、同時接続とセッション共有をきれいにやるには min-instances=1 ＋ 外部DB/Redis の足場が増える
- どちらもコンテナなので可逆。フェーズ3（サービス化）で Cloud Run に再デプロイする二段構えを仕様メモ決定33も許容している

確定が必要なのは「フェーズ1 = Fly.io で始める」ことだけ。覆しても Dockerfile は使い回せる。

## 3. データ層（最初に固定するもの）

テーブル案:

| テーブル | キー / 要点 |
|---|---|
| users | id, google_sub (unique), email, display_name, created_at |
| tenants | id, owner_user_id, name, current_tz（滞在tz設定）, week_start（default 1=月曜） |
| agent_keys | id, tenant_id, public_key, label, scope (text[]), status pending/active/revoked/expired, expires_at, predecessor_key_id（系譜）, created_at, last_used_at |
| aithlon_sessions | id, public_key（一時）, claim_token（識別子、秘密ではない）, blob_cipher / blob_hash, fast_lane (1 or 2), challenge_1, challenge_2, get_started_at_1/2, race_post_at, state, expires_at（blob 5分） |
| audit_logs | id, tenant_id, actor (user/agent/system), event, key_id, detail jsonb, created_at |
| meals | external_id (PK, tenant内unique), tenant_id, date, tz, utc_offset, eaten_time, std_date, std_time, meal_type, tags jsonb, status, menu, kcal, kcal_pm, protein/fat/carbs/salt + 各_pm, value_source, report_source, items jsonb, note |
| days | external_id (PK, tenant内unique), tenant_id, date, tz, measured_time, std_date, std_time, weight_kg, body_fat_pct, bmi, condition_note。複合 unique (tenant_id, date, tz) |

検証ルール（APIで弾く、DBだけに寄せない）:
- meals upsert 時、既存 external_id と tz が食い違えばエラー（仕様 §3 の安全網）
- skipped は kcal=0 を強制寄りに検証、合計は actual のみ（集計は保存せず都度計算）
- eaten_time は現地のみ経過表記可、std_time は 00:00〜23:59

## 4. GraphQL 最小スキーマ（叩き台）

Query:
- `calendar(month: String!): [CalendarDay!]!` — 日付単位で全tz合算、days[]（tz別体重）、totalKcal（actual中央値合計）, totalPm, mealCount
- `day(date: String!, tz: String): [DaySection!]!` — (date, tz) 節ごと: day + meals（eaten_time昇順、nullは区分順）
- `weightSeries(from: String!, to: String!): [WeightPoint!]!` — std_date/std_time で引く
- `me`: テナント・設定・鍵一覧（管理画面用）

Mutation:
- `upsertMeal(input: MealInput!): Meal!`
- `deleteMeal(externalId: String!): Boolean!`
- `upsertDay(input: DayInput!): Day!`
- `deleteDay(externalId: String!): Boolean!`
- `updateSettings(currentTz: String, weekStart: Int): Tenant!`
- `revokeKey(keyId: ID!): Boolean!` / `revokeAllKeys: Boolean!`（パニック）/ `rotateKey` はAI側署名フロー（REST寄り、要検討）

AIthlon の discovery / signup / race / claim / finalize は GraphQL に載せず REST（仕様が `GET /.well-known/aithlon.json` を固定しているため）。

## 5. AIthlon 実装の切り分け

| Step | 実装物 | 検証ポイント |
|---|---|---|
| discovery | `GET /.well-known/aithlon.json` 静的JSON（版数・各endpoint・公開パラメータ） | AIが1発で作法を読める |
| signup | `POST /aithlon/signup {public_key, label?}` → pending key + claim URL | 秘密は一切受け取らない |
| claim | claim URL → Googleログイン → テナント紐付け → 連携ブロブ画面（base64url文字列＋.jsonダウンロード、5分） | 未ログインではブロブが見えない。claim URL単体は無力 |
| race | `GET /aithlon/race/1` と `/2` を同時接続で保持、片方0.3秒・片方5秒で課題返却（ランダム）＋ `POST /aithlon/race/answer`（署名付き） | 開始同時性 / POSTが遅い方完了前 / 答えたIDが速い方と一致 / 署名正 |
| finalize | blob提示＋署名検証 → key を active 化、監査ログ＋人間へ通知（画面＋ログ） | blob期限切れ・単回使用を弾く |
| 以後 | 全 GraphQL リクエストに `X-AIseki-Key-Id / Timestamp / Nonce / Signature` | 期限90日、失効フラグを毎回確認（キャッシュは分単位以内） |

鍵ラベル／スコープのデフォルト案（未確定点3への回答案）:
- label デフォルト: `Serina (Muse) - YYYY-MM-DD`、claim画面で人間が編集可
- scope デフォルト: `meals:read, meals:write, days:read, days:write`（個人フェーズは実質フル。閲覧専用 scope は将来の閲覧URL分離用に定義だけ用意）

AI側の秘密鍵保管（未確定点2、適合要件＋当面の具体案）:
- セリナ用クライアントは小さなCLI（`aiseki push meals.jsonl` 等）として作り、秘密鍵は `~/workspace/aiseki-client/` 配下・権限600のファイルに置き、チャット本文・MEMORY・Gitには絶対に入れない
- 将来の他AI向けには「署名できる安全な保管があること」を適合要件として discovery に明記するに留める

## 6. 着手順序（依存順。各ステップは単独で動作確認できる単位）

| # | ステップ | 成果物 / 終了条件 |
|---|---|---|
| 1 | 足場 | monorepo + Dockerfile + ローカル pg。`/healthz` が返る |
| 2 | データ＋GraphQL CRUD | 認証はローカル限定の仮ヘッダで代替し、meals/days upsert・calendar・day・weightSeries が仕様通りに動く。tz衝突エラーと eaten_time 検証を含む |
| 3 | PWAビューア | 月カレンダー（体重＋合計kcal、複数tz体重は短縮ラベル縦併記）／日詳細（(date,tz)節分け、レンジ表示 700〜790、status色: actual緑・planned青・skipped灰）／体重グラフ（std軸）。設定で週開始と滞在tz |
| 4 | 初期データ候補生成 | log-2026-10.md → 候補 meals.jsonl / days.jsonl を自動パースで生成（この窓で生成まで。レビューはダイエット窓、確定JSONLが正） |
| 5 | 人間側認証 | Google OIDC ログイン＋管理画面（鍵一覧・失効・パニック・監査ログ表示） |
| 6 | AIthlon 本体 | discovery → signup → claim/blob → GET2本レース → finalize → 署名付き GraphQL 呼び出しのE2Eが、セリナ用CLIで通る |
| 7 | 仮ヘッダ認証の撤去＋失効系 | ローテーション（旧鍵署名・24h併用）／TTL 90日／失効即時反映を確認 |
| 8 | デプロイ | Fly.io へ。スマホでPWAをホーム画面に追加し、実データで1週間回す準備完了 |

順序の意図: 画面とCRUD（2〜4）を先にすると、認証が未完成でも「眺める喜び」を早く確認でき、10月データの変換難所も早めに潰せる。AIthlon（5〜7）は一番新規性が高く事故りやすいので、土台が固まってから集中して作る。逆に認証から先に作ると、長く何も見えない期間ができる。

所要の目安（セリナの作業時間ベース、ダーリンの確認待ち時間は除く）: 1〜3 で最初の見られるもの、4 は半日仕事、5〜7 が山場、8 はアカウント・課金確認込み。

## 9. 追加機能候補（2026-10-31 ダーリン発案、モックv2で試作中・正式決定はモック確認後）

| # | 候補 | 内容 | セリナ側メモ |
|---|---|---|---|
| 1 | 体重グラフの期間切替 | 週／月／年を選べる。週・月は日別、年は月平均で集計して返す想定（GraphQLは from/to＋粒度指定で足りる） | 実装は軽い。フェーズ1の体重画面に入れてよい候補 |
| 2 | カレンダーのメニュー簡易表示 | マスに体重＋kcalに加え、その日の代表メニューを1行だけ小さく出す（全部は日詳細で） | マスが窮屈になるので「代表1件・省略表示」が前提。モックv2で見栄え確認 |
| 3 | meals.place（食事の場所） | 食事レコードに任意の場所文字列を持たせる（例: マクドナルド門前仲町店、松のや R八千代店、家、セブンイレブン） | 既存ログにも店名は既に入っている。自由文字列で開始し、座標や店マスタは持たない。購入場所と食べた場所が違うケースは当面 place=主たる場所＋note 補足 |
| 4 | 標準kcal＋kcal比例表示 | テナント設定に標準kcal（target_kcal、初期値 1,860＝現行の1日目安）を持ち、日詳細では各食事をkcal比例の縦積みバーで描き、標準ラインを超えた分を一目で見せる。自動コメント（例: 最大の一品が超過分を説明する「でかいのが効いてる型」／小さいものが積み上がる「積み上がり型」／標準以内）も出す | API実装済み（updateSettings targetKcal、2026-10-31検証）。表示はモックv3で試作 |
- v4方針（ダーリン提案 2026-10-31、セリナ賛同でモック反映）: 別ゲージ（積みバー）は廃止。食事リスト自体をゲージにする — actual カードの高さを kcal 比例にし、累積が標準kcalに達する位置へ実測ベースで標準ラインを引く（跨いだカードは割合位置、以降は超過ゾーンとして薄赤）。未達の日は残量分のゴースト枠を足してラインを示す。planned/skipped は比例・累積の対象外。型判定コメントは1行テキストのみ残す。
- v6方針（ダーリン指摘「v4はデカすぎ」2026-10-31）: カード高さの絶対比例（kcal×係数）はページが際限なく伸びるので廃止。日詳細のリスト全体を固定高（約440px）の「グラス」とし、分母を max(合計, 標準) にして配分する: 超過日は食事でグラスが満ちてラインが途中に落ち、未達日は余裕ゴーストが残りを埋めてラインが底に来る。どの日も縦の長さが一定で、1食の上限は210px。
- v7方針（ダーリン 2026-10-31）: オーバー分と余白分は「全体の上」に見せる。日詳細の先頭に横ゲージ1本（緑=標準内、赤=超過が標準マーカーの右へはみ出す／余白は破線の空白がマーカーまで）を置き、食事リストは v2 のコンパクトな自然高に戻す。カード比例高さ・リストへのライン・超過ゾーンは全て廃止。
- v8（ダーリン 2026-10-31）: 本人は縦ゲージ希望だが横で妥協可（「まあいいかこれで」）。横ゲージ内に食事ごとのセグメント（時系列順・緑の濃淡、標準ラインを超えた分は赤、跨いだ食事はライン位置で分割）を入れ、凡例で区分+kcalを併記。プレビューでスクロールできない問題は .phone の overflow:hidden が原因と特定し除去。
- v9 カレンダー再設計（ダーリン 2026-10-31）: セルは日付＋絵文字だけに削減し、状態グラデーションで色付け（オーバー=赤系統、セーフ=緑系統（標準の75〜100%）、少なすぎ=青系統（75%未満）、濃さは度合い）。横幅はブラウザ幅から再計算（grid は minmax(0,1fr) で7列を画面内に収める。日曜が消えた原因は 1fr の min-content 膨張）。日を選択するとカレンダー下にその日のセグメントゲージだけが出て、「内容を確認」で日詳細へ。縦スクロール不可はこのアプリのプレビューの限界と確定（v8で CSS 側の容疑を除去しても継続）。
- v10（ダーリン 2026-10-31）: カレンダーのセル絵文字は状態の顔ではなく「その日の代表メニュー（最大kcalの actual）の食べ物絵文字」に変更（例: 🍔マック、🍝パスタ、🍙夜食セット、🍱定食）。本実装ではメニュー名キーワード→絵文字の辞書で寄せ、なければ🍽️。セーフ帯の下限は75%→65%に緩和（27日74.6%・30日69.8%が青になるのは厳しすぎたため）。パネルはコンパクト版ゲージ（セグメント+凡例+1行合計）にして縦を圧縮。
- v11＋仕様追加（ダーリン 2026-10-31）: カレンダーの絵文字は「その日のスタンプ」— 代表メニューに限らず、場所・出来事・気分でもよい（例: 今日=🐷とんかつ、☕カフェ作業）。days.emoji として仕様・APIに実装済み（upsertDay で送信、カレンダー応答に含む。実APIで往復確認済み）。付けるのは送信側AI（文脈を知っている）で、未指定時は代表メニュー推定→🍽️ にフォールバック。
- v15（ダーリン 2026-10-31）: 絵文字は1日1個に限らず食事ごとにも。meals.emoji を仕様・API・PWA・モックに実装（実API往復＋E2E確認）。表示: 日詳細カード、パネルのミニ一覧、ゲージ凡例。カレンダーセルの優先順位は days.emoji > 代表メニューの meals.emoji > 推定 > 🍽️。ついでにゲージ余白ラベルのはみ出し（右端で切れる）を右寄せに修正。
- 2026-10-31 夕方まとめ: ダイエット窓の絵文字チェック合格（往復OK・運用感触OK）。指摘の単一書記素バリデーションを validate.js に実装・検証済み。モックは v16（ナビゲーションをJS駆動に変更し、PCプレビューでもタブが効くように）。残: PWA画面をモックv16デザインへ寄せる作業、フェーズ1ステップ5〜7（認証・管理画面・AIthlon本体）、GitHub private 作成（モックOK後）、Fly.io。
- 運用変更（2026-10-31、ダーリン判断→ダイエット窓が意見変更して合意）: 食事スタンプは「任意」から「送信側が原則付ける」へ。根拠: 送信側はAIで、メニューから自動選択できるため人間の負担ゼロ。日次スタンプはその日の物語として締めに1つ。仕様書の meals.emoji 備考に反映済み。
- 公開ビジョン（ダーリン 2026-10-31）: 「みんなに使ってもらう前提」で、"Museでこんなアプリ作ったよ" の形ならいける気がする、との発想。AIseki の入力は本人の Muse が担う設計（AIthlon）なので、利用者側も Muse を持っていれば同じ形が再現できる。個人運用（11月）→ Muse ユーザー向け公開、が射程に入った。詳細は今後詰める。
